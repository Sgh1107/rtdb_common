## 2. 总体结论（先读）

1. **工程整体质量高**。分层清晰（platform/infra/storage/engine/API）、协议文档与实现互指、
   测试基础设施（failpoint 崩溃注入 + 混沌子进程 + ASan/UBSan + 覆盖率）在同类自研存储中属于优秀水平。
2. **发现 3 个高危正确性缺陷**（均为"静默数据丢失/损坏"类，且都位于 M2 冻结的核心路径上）：
   - **P0-1**：批量写入的 WAL 记录在环满覆盖协议下可被**中途丢弃**，破坏批原子性与持久性承诺
     （`UpsertBatch`/`ExecuteBatch` 对 > 环容量的批次）。
   - **P0-2**：行记录**发布之后**二级索引维护失败时，调用方 `ReleaseStaged` 会**释放已发布记录仍引用的变长块**，
     且恢复重放因幂等跳过不会修复（数据损坏持久化）。
   - **P0-3**（修复冲刺期在 A1 分析中**新发现**，见 §4.8）：WAL 环尾垫片回绕的旧空间判据
     只核对"总量"，未核对回绕落位约束，特定 head/tail 位形下记录会**覆盖环内既有数据**。
3. **发现 4 个中危问题**：update 成功路径 `allocated_vars` 不清空（契约破口，与 P0-2 同源）、
   `Engine::Impl::stores` 数据竞争（与 `engine.hpp` 线程安全声明矛盾）、Windows `Always` 档持久性缺口、
   行式 API 列类型静默强转。
4. **明确回答"继续开发 vs 先测试"**：
   **不建议直接进入 M3，也不建议停下做全面详细测试**；建议先执行一次**约 2 人日的修复冲刺**
   （修复 P0/P1 + 补定向回归用例 + CI 增强），验收通过后按原计划进入 M3。
   理由见 §7：现有测试体系的问题不是"量"而是特定场景盲区（缺陷恰好全部落在盲区内），
   而 M3 的服务化会把触发条件（大批次、内存压力、多线程）放大一个量级。

## 4. 缺陷清单

### 4.1 【P0-1】批量 WAL 环满覆盖协议中途丢弃未提交批前缀

**位置**
- `src/engine.cpp:195-207` `EnsureRingSpace`（环满 → `FlushNow` → 推进 `checkpoint_seq` → `DropAllRetained`）
- `src/engine.cpp:254-258` `WalAppendRowOp` 每条记录都调用 `EnsureRingSpace`
- `src/engine.cpp:816-828`（`UpsertBatch` WAL 段）与 `src/engine.cpp:1097-1108`（`ExecuteBatch` 同构）
- `src/storage/wal_ring.cpp:178-181` `DropAllRetained`（tail 直接对齐 head，**无条件丢弃全部保留记录**）
- `src/storage/group_commit.cpp:29-42` `FlushNow` 只覆盖进入时的 `committed_seq`

**机理**（逐步推演）
1. 批的三段式协议是：`BEGIN` → N×行操作 → `COMMIT` → 统一应用 → `MarkCommitted`。
   在 COMMIT 之前，本批已写入环的记录 seq **大于** `committed_seq`（上次提交位置）。
2. 每条行操作追加前都会 `EnsureRingSpace`；环满时它执行 `FlushNow`（只承诺覆盖 ≤ `committed_seq`
   的页）+ 推进 checkpoint + **`DropAllRetained`（丢弃环内全部记录，含本批的 BEGIN 与前缀行操作）**。
3. 此后本批继续追加剩余行操作与 COMMIT。环内从此**缺失 BEGIN 与前缀行操作**，出现三种失效形态：

| 形态 | 环内残留 | 恢复（重放）行为 | 后果 |
|---|---|---|---|
| A：COMMIT 已写、此后整机断电（未再全量刷盘） | 后缀行操作（无 BEGIN）+ COMMIT | 后缀作独立记录重放；前缀无 WAL、页未落盘 | 前缀行**静默丢失**，但 `UpsertBatch` 已返回成功；镜像部分写回时批内状态**非原子** |
| B：COMMIT 前崩溃（如注入点 `wal.batch.wal_mid`） | 仅后缀行操作（无 BEGIN、无 COMMIT） | 无 BEGIN ⇒ 后缀被当作**裸记录逐条应用** | **未提交批被部分持久化**，直接违反"无 COMMIT → 恢复整批作废"（`src/storage/wal_ring.cpp:360-364`） |
| C：`DropAllRetained` 恰在 COMMIT 追加时触发 | 仅 COMMIT | COMMIT 无批可提交，重放**零操作**；`valid_end = commit.seq`（`wal_ring.cpp:377-378`） | 整批丢失且 `committed_seq` 水位**越界承诺**（水位说已提交，WAL/镜像没有） |

**触发条件（数值）**
- 环为固定单 slab 分配：64KB 块 − 64B 环头 = 记录区 **65,472B**（`kDefaultWalRingBytes`，`src/storage/wal_ring.hpp:68`）。
- 每条记录 = 56B 头 + 载荷 + 4B CRC。2 列 int64 的行记录 84B ⇒ **批内约 779 行**即触发（环近乎空时）；
  若环内已有未覆盖记录（高写入速率下的常规状态），更小的批也会触发。
- **现有 512 行块 bench（8 列，记录约 132B，共 67,648B）已越过阈值**——每次迭代都在走这条路径，
  仅因进程内 apply 独立于 WAL 而未暴露（`tests/unit/test_main.cpp:820-914`，注释自称"64KB 行数据区"，实际 WAL 侧同样受限）。

**影响**：批原子性与持久性承诺（docs/08 §2-D3"COMMIT 先于数据页"）在容量边界处失效；
形态 B 直接把"未提交批"变成部分可见数据，且发生时无任何错误返回/告警。

**修复建议（推荐组合）**
1. **批前预留（必做）**：在 BEGIN 之前计算整批 WAL 字节
   （`RecordBytes(BEGIN) + Σ RecordBytes(op_i) + RecordBytes(COMMIT)`）：
   - 总量 > 记录区容量 → 直接以 `kLimitExceeded` 拒批（零 WAL 副作用，不毒化，错误可归因）；
   - 否则调用 `EnsureRingSpace(总量)` 做一次"腾环"（此刻根锁在手、环内不存在未提交批，drop 安全）。
   预留成功后，批内各条追加的总占用受预留约束，`HasRoomFor` 恒成立，**mid-batch drop 不再可能发生**。
2. **纵深防御（建议）**：`Impl` 记录"批进行中"状态（`BEGIN` 已写且未写 `COMMIT`）；
   `EnsureRingSpace` 在该状态下若必须 drop → 返回 `kLimitExceeded` 并毒化，**宁可失败不丢数据**。
3. 长期项（不阻塞 M3）：环容量可配置/可分片扩展，随布局演进一并评估。

**回归测试建议**
- 新增用例族"批 × 环容量边界"：批量 = 环容量 ±10%（环近乎空 / 环半满两档），断言：要么拒批（无副作用），
  要么成功且 **崩溃重启后整批原子一致**（含 `committed_seq` 不回退、不越界）。
- 把现有 512 行块 bench 场景升级为崩溃恢复断言变体（当前它已在危险区运行却无持久性校验）。
- 增加批内不变量用例：批完成后扫描环，`BEGIN/COMMIT` 必须配对，批内记录数 == BEGIN 申报的 count。

### 4.2 【P0-2】记录发布后二级索引失败 → 释放已发布记录的变长块（重放不修复）

**位置**
- `src/storage/table_store.cpp:629-635`（insert：`*ver` 已置偶数、主键已插入后，`SecKeysOfRow`/`InsertSecKeys` 失败仅 `return`）
- `src/storage/table_store.cpp:660-664`（update：`*ver` 已置偶数后，同上）
- 调用方释放：`src/engine.cpp:556-557 / 915-916`（单行 Insert/UpdateByKey，应用失败即 `ReleaseStaged`）、
  `src/engine.cpp:851 / 1132-1133`（批回滚含**失败项自身**）
- `src/storage/table_store.cpp:693-707` `ReleaseStaged`（无条件释放 `allocated_vars`）
- 重放幂等跳过：`src/storage/table_store.cpp:727-730`（`found && existing == row_no → kOk`），
  update 变体由 `*ver < row_ver` 不成立而跳过重写（`:733-747`）⇒ **重启不能修复**

**机理**
1. insert 路径的发布序为：`*ver=偶数`（`:609`）→ 主键插入（`:619`）→ **二级索引维护**（`:629-635`）。
   若 `SecKeysOfRow`/`InsertSecKeys` 失败（现实触发：共享内存接近满，二级索引 B+ 树节点分配失败 `kOutOfMemory`），
   函数仅返回错误**不回滚已发布内容**（注释意图即"WAL 已先行，Open 重建自愈"）。
2. 但调用方把"应用失败"统一当作"可完全回滚"：`ReleaseStaged` 释放 `st->allocated_vars`——
   这些变长块**已被发布中的行记录引用**。insert 变体还会因 `row_no+1 == row_count` 触发
   `row_count--`（`:701-704`），**已发布行槽被登记为可复用**，后续 insert 将覆写同一槽位。
3. update 路径同构：旧键已摘除、新键可能半插入后失败，调用方同样释放新的变长块。
4. 引擎随后毒化（拒写），**但重启无法收敛**：insert 变体主键已在索引 → 重放幂等跳过；
   update 变体版本已到位 → 只补索引不重建记录。被释放的池块随自由链**再分配**给后续行 ⇒ 数据静默损坏持久化。

**影响**：行数据（变长列）读到他人内容/空值；行槽会计错乱导致后续写入覆盖已发布行；
池结算与数据引用不一致。属于"重启不修复"的持久性损坏。

**修复建议**
1. **明确发布点语义（必做）**：在 `ApplyStaged` 内把"`*ver=偶数`"定义为不可回滚点；
   发布点**之后**的任何失败路径在 `return` 前执行 `st->allocated_vars.clear()`
   （所有权已转移给行记录；错误由调用方毒化 + Open 重建二级索引自愈——与现有注释意图一致，只是补上所有权转移）。
2. **防御层（建议）**：`StagedRowOp` 增加 `published` 标志；`ReleaseStaged` 在 `published` 时
   跳过变长块释放与行槽回退，杜绝未来调用方误用。insert 的 `wal.index.insert` 注入分支
   （`:612-618`，发布前回滚、数据已清零）保持现状即可。
3. update 中 `SecKeysOfRow(old_keys)`（`:644-645`，发布前）失败仍可安全释放，维持现状。
4. 增加 failpoint `wal.secidx.after_publish`（ErrorPoint）使该路径可注入、可测。

**回归测试建议**
- 用例：含二级索引 + 变长列的表；注入发布后失败 → 断言 `Upsert/Update` 返回错误、引擎毒化拒写；
  重开后行值与变长列**与未注入对照完全一致**；随后继续写入并校验池结算（`alloc_count/alloc_bytes` 增减对称、无 `kInternal`）。
- 另补"insert 失败后行槽账"检查：后续 insert 的 `row_no` 不得与已发布行冲突。

### 4.3 【P1-1】update 成功路径不清 `allocated_vars`（契约破口，P0-2 同源）

**位置**：`src/storage/table_store.cpp:640-668`（update 成功路径缺 `clear`；insert 路径 `:637` 有）
对照批回滚注释（`src/engine.cpp:850`、`:1130-1131`）声称"已应用项 `allocated_vars` 已清空，跳过"——
**该前提对 update 不成立**。

**机理与影响**：成功应用后 `allocated_vars` 仍列着已归属行记录的块。
当前代码仅因"批回滚跳过已应用项 + 单行失败路径恰好不清"而侥幸未双释放；
任何未来在"成功后"调用 `ReleaseStaged` 的路径（重构、工具代码、`TableStore::Insert` 兼容封装）都会释放活块。

**修复**：`:666` `ReleaseRecordVars(st->old_rec.data())` 之前/之后补 `st->allocated_vars.clear();`，
与 insert 路径、与 P0-2 的"发布即转移所有权"不变式统一。

### 4.4 【P1-2】`Engine::Impl::stores` 无锁并发写（与线程安全声明矛盾）

**位置**：`src/engine.cpp:107-149`（`std::unordered_map` 懒加载 + `emplace`）；
读路径在根锁外调用 `StoreFor`：`GetByKey`（`:869`）、`ContainsKey`（`:984`）、`Scan`（`:998`）、
`GetBySecondary`（`:1196+`）、`Upsert` 的存在性分流（`:587/616/622`）。
对照承诺：`include/rtdb/engine.hpp:46`"同一实例可被多线程使用"。

**机理**：两个线程首次访问同一表（或任意两表同时首访）并发执行 `find/emplace`，属无同步数据竞争（UB），
可能损坏哈希桶结构。CI 无 TSan，ASan/UBSan 检测不到。

**修复**：（最小）给 `stores` 配互斥，仅保护 `find/emplace/取指针`——
`unique_ptr` 元素地址稳定，取出后的 `TableStore*` 使用不受影响，读性能几乎无损；
（可选优化）`Open` 时按目录预热全部表，使运行期只读。
并新增 Linux TSan CI job（配合 1~2 个"多线程首访同表 + 读写并发"烟雾用例）。

### 4.5 【P1-3】Windows 刷盘缺 `FlushFileBuffers`（Always 档持久性缺口）

**位置**：`src/platform/win32/shared_memory_file_win32.cpp:56` 仅 `FlushViewOfFile`；
对照 POSIX `msync(MS_SYNC)`（`posix/shared_memory_file_posix.cpp:45`，对文件数据足够）。

**机理**：`FlushViewOfFile` 只把脏页刷入文件系统缓存，不保证到设备；
断电语义（`Always` 档的核心承诺）在 Windows 上不成立（进程崩溃/kill -9 无影响，属断电场景差异）。

**修复**：Win32 flush 路径追加对文件句柄的 `FlushFileBuffers`；并在 docs 的档位语义表标注平台差异。

### 4.6 【P1-4】行式 `Insert/Update` 不做列类型校验（静默强转）

**位置**：`src/storage/table_store.cpp:311-364` `BuildRecord` 直接 `as_int()/as_real()/as_bytes()`；
`include/rtdb/column_value.hpp:111-120` 取值为成员直读、不校验实际类型 kind。
对照 `UpsertBatch` 有 `PayloadTypeCompatible` 校验（`src/engine.cpp:704-705`）。

**机理与影响**：行式 API 传错类型（如 Text 值塞 int64 列）→ `int_` 默认值 **0** 静默入库；
int 值塞变长列 → 空串入库。用户无感知。`CheckRowWidth` 只校验列数。

**修复**：在 `BuildRecord`（或其调用前沿）按列类型校验 `ColumnValue` 实际 kind，错配返回 `kInvalidArgument`
（复用与批量路径一致的兼容矩阵）；补单测覆盖"每类列 × 错类型"。

### 4.8 【P0-3】（修复冲刺期新发现）WAL 环尾垫片回绕越界覆盖

**位置**
- `src/storage/wal_ring.cpp:46-48` `HasRoomFor`（旧判据：`area ≥ rec && area - PendingBytes() ≥ rec`，只看总量）
- `src/storage/wal_ring.cpp:108-131` `WriteTailPadAndWrap` / `Append`（`area - head_pos < rec` 时写垫片回绕，记录从 0 起写）

**机理**
1. 环为线性缓冲，保留数据占 `[tail_pos, head_pos)`（回绕时含环尾与环头两段）。当剩余连续空间
   `area - head_pos < rec` 时，写方先写"垫片"填至环尾、然后**回绕从 0 起**写记录。
2. 旧判据在"总量足够"时放行，**未检查记录能否容身 `[0, tail_pos)`**：当 `rec > tail_pos` 时，
   回绕后的记录覆盖 `[tail_pos, head_pos)` 的既有数据（尾部保留段被静默冲掉）。
3. 触发位形：`head_pos ∈ (area - rec, area - rec + tail_pos]`。稳态下 `head_pos` 随覆盖协议的
   逐周期丢弃下漂（新 tail 位置 = 丢弃时的 head），窗口窄但可现实触发（记录 ≤ ~33KB 量级）。

**影响**：环内既有（已提交）记录被静默覆盖；扫描在覆盖点 CRC/seq 连续性校验失败 → 恢复重放把
其后记录一并作废——丢失面 = 覆盖点之后全部未被 checkpoint 覆盖的提交，属持久性损坏。

**修复**（已落地）
- `HasRoomFor` 与 `Append` 统一为单一判据：总量足够之外，当 `area - head_pos < rec` 时要求 `rec ≤ tail_pos`；
- 新增 `area_bytes()` 访问器（批前预留需要，见 A1）；
- `Append` 直接复用 `HasRoomFor`。

**回归**：`WalRingTest.LargeRecordWrapNeverOverwrites`——构造 `head` 落入覆盖窗口，断言
`HasRoomFor == false`、`Append == kLimitExceeded`、随后扫描 seq 严格连续、连续可达小记录仍可写。
（已做判别力验证：回退旧判据后本用例转红——记录被覆盖、扫描中断。）

## 5. 为什么 CI 全绿仍存在上述缺陷（测试与 CI 盲区分析）

1. **崩溃/混沌用例的批规模远小于阈值场景**：混沌 batch 场景 10 条操作（`tests/unit/test_main.cpp:296-305`），
   块崩溃用例的批 8 行（`tests/unit/test_main.cpp:340-356`，`tests/unit/test_record_block.cpp:378-392`），
   全部远低于 P0-1 的触发线（~779 行）。
   而唯一进入危险区的 512 行块 bench 只测吞吐、不校验持久性。
2. **P0-2 的失败点没有注入通道**：现网 failpoint 清单（18 处）中，`wal.index.insert` 位于发布**前**分支；
   发布**后**的二级索引维护失败无注入点，且单测无法自然制造（需逼近内存耗尽）。
3. **无 TSan**：数据竞争类缺陷（P1-2）对 ASan/UBSan 不可见；现有并发测试缺失（多为单线程 + 背景 flush）。
4. **覆盖率是全局行覆盖**：不度量"错误路径/故障分支"是否被走到；P0-1/P0-2 恰在低覆盖分支上。
5. **平台语义差异无测试**：Windows `Always` 档断电语义（P1-3）本质不可在 CI 复现，只能靠实现审查。
6. **环状态机只在"整圈填充"路径上被测**：既有 `WrapPadAndSeqContinuity` 是 `tail_pos=0`（或近环尾）
   的良性位形，未覆盖"垫片回绕 + `tail_pos` 小于记录长度"的交界位形（P0-3 恰在其盲区）。
   P0-3 由修复期对 `HasRoomFor`/`Append` 的逐分支走查发现，非常规测试可自发命中。

**修复冲刺的封堵（见 §8）**：盲区 1/2/6 已补定向用例（批容量边界 777/778、近满腾环、回绕覆盖、
发布后失败保读/重开/池归属），盲区 3 已补 TSan job 与并发用例，盲区 2 的注入点
（`wal.secidx.after_publish`）已落地。
