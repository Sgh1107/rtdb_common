## 2. 核心技术决策（含 wal-kv 对照）

### D1 WAL 落点与持久化语义（已拍板 ✅ 2026-08，选项 A）

docs/02 §3 布局将 WalRing 放在**映像内**；docs/03 §3.2 快照 = "SuperBlock 记 checkpoint_seq
后 mmap 文件整体 rename"。两者组合的语义必须先说清，否则崩溃恢复承诺无法落地：

- **进程崩溃（kill -9，即 M1 出口验收的注入手段）**：mmap 共享页与文件背衬在进程死亡后
  依然一致，WalRing 与数据页**零丢失**——per_second 档在进程崩溃口径下同样是零丢失，
  这是 docs/05 验收"崩溃注入(kill -9×随机点)后数据零丢失(per_second 档)"的准确读法；
- **机器崩溃（断电/内核 panic）**：只有已 flush 到盘的前缀存活。三档语义据此定义：
  | 档位 | 提交返回时 | 断电承诺 |
  |---|---|---|
  | always | 本组提交已 flush 全映像（头部+WAL+数据） | 已确认提交零丢失 |
  | per_second（默认） | 写入页缓存即返回，后台节流 flush | 丢最近 ≤1s 窗口；进程崩溃不受影响 |
  | never | 不主动 flush | 仅进程内一致 |
- **WAL 职责**（影像内环形）：① 组提交聚合与等待者唤醒；② 重启时重放
  `(checkpoint_seq, committed_seq]` 修复"数据已改、索引/目录半更新"的不一致；
  ③ M3 订阅的 ChangeLog 源（与 docs/02 §5 同环复用）；
- **覆盖协议**：环写满或即将覆盖 `checkpoint_seq` 之后未 flush 的记录时，触发强制组刷
  并推进 checkpoint（"覆盖前先落盘"），保证任意时刻重放区间完整可用；
- **不引入** sidecar WAL 文件（wal-kv 模式）：那是文件型存储的正确选择；本库数据载体
  本身就是内存映像文件，双写两份日志只会引入一致性问题。wal-kv 的**契约**照搬，
  **载体**不照搬。

> **拍板记录（2026-08）：采纳选项 A，维持上表三档语义。**
> 论证结论：零丢失能力由 always 档提供（实例级按部署场景选择）；per_second 保持
> 窗口语义以兑现 docs/05 §4 的 P99 ≤ 10μs 热路径目标。拒绝 sidecar 方案的两个
> 硬理由：① fdatasync 延迟量级（百 μs~ms）与组提交在嵌入单写者场景无批可攒，
> 物理上进不了 10μs 预算；② 本库事实源是 mmap 原地修改的映像页且存在跨进程
> 直读读者，断电页撕裂必须页级 checksum/doublewrite 才能防护——sidecar 方案
> 真实成本 +4~6 周（M1 翻倍），域上实时库定位为"当前态"存储，历史/SoE 归下游。
> 行业先例：Redis AOF everysec 同语义。sidecar 零丢失升级保留为 M2 独立立项
> 通道（届时以 bench 数据支撑复评）。

### D2 写路径顺序与幂等重放（正确性核心）

采用 wal-kv 的确认契约思想，适配到映像内写路径：

```
取表锁 → WAL 追加（带 seq/CRC，先于数据修改，write-ahead）→ 修改数据页/索引
       → commit 标记（推进表 committed_row_count/全局 committed_seq）
       → 按档位 flush → 唤醒组提交等待者 → 返回
```

- 重放器只做 **redo 幂等重放**：以 `row_no + row_version` 判重，重复应用无副作用；
- 覆盖 docs/06 §3 全部注入点：`Insert前 / WAL追加中 / commit标记前 / 索引更新一半 /
  snapshot rename中`——WAL 追加失败或 commit 前崩溃 → 重放将该行推进到"已存在"或跳过，
  两种结局均与 `committed_seq` 自洽；
- **毒化状态**（wal-kv `poisoned` 模式）：WAL 环写失败或校验失败后引擎拒绝一切写
  （新增 `Err::kPoisoned = 301`），避免在不确定尾部上继续追加；读不受影响。

### D3 记录格式（对齐 docs/03 §3.2，借鉴 wal-kv 编码纪律）

`WalRec{ seq:u64, ts_ns:u64, op:u8, table_id:i64, row_no:u64, row_ver:u64, payload_len:u32, payload }`：

- 逐字段小端显式编码（禁止整 struct 落盘）——wal-kv storage_format 的铁律，直接沿用；
- 每条记录 16B 头 + payload + CRC 尾（复用 `infra::Crc32`；wal-kv 用 CRC32C 是为硬件加速，
  本库保持单一 CRC 实现避免双标准，备注留 M4 优化）；
- 批量原子性：`BATCH_BEGIN + N×op + BATCH_COMMIT` 三段式（wal-kv WriteBatch 同构），
  恢复时见到无 COMMIT 的 BEGIN 即整批作废——天然适配环形覆盖。

### D4 Catalog 与目录事务

按 docs/03 §4.1：双 B+树（`StringBTree name→table_id`、`IntBTree id→desc_off`）+
描述符定长数组；目录变更持 `meta` 互斥（复用 M0 `ShmRootMutex`，低频场景粗锁够用）
并**先写目录 WAL 再改目录**，崩溃后由重放还原。上限（65535 表/128 列/16 索引）
进 SuperBlock 配置字段（版本递增）。

### D5 在线加列与旧句柄（对齐 docs/02 §3 要点 3）

列定义只追加不重排：初始列区 + `ext_col_off` 扩展区 + 默认值位图；行内新列读默认值，
旧 `TableHandle` 绑定 `data_layout_ver` 快照继续读。wal-kv "旧读者 pin 住旧 generation fd
安全读完"的语义在本库由 mmap+布局版本天然获得，无需 pinning。

## 5. wal-kv 经验移植清单

| wal-kv 机制（源文件） | 本库 M1 落点 |
|---|---|
| 写确认顺序 `append → sync → publish → return`（database_engine） | D2 写路径顺序；确认点=flush 档位语义 |
| tail-repair vs corruption 分类（wal_scanner/recovery） | WalRing 环尾可修复、中部损坏拒绝打开（kPoisoned/kBadSuperBlock） |
| BEGIN/COMMIT 原子批（WriteBatch） | `ExecuteBatch` 三段记录，单次 flush |
| failpoint 确定性崩溃 + crash matrix（failpoint.cpp/scripts） | `RTDB_FAILPOINT` 编译开关 + W6 混沌脚本；默认构建不启用（防"未跑冒充通过"） |
| poisoned 实例状态 | D2 毒化：写路径故障后拒写保读 |
| 逐字段小端编码铁律（storage_format） | D3 记录格式纪律 |
| generation+sequence 操作标识（OperationId） | 全局 committed_seq + 表级 row_version；M3 订阅游标直接复用 |
| RecoveryLimits 预算 | M1 简化：环容量上限+强刷退化；完整预算 M4 |
| 每周 rotation/recovery/corruption 测试方法论 | W4/W5 测试集直接对标其 `rotation-tests`/`recovery-tests`/`corruption-tests` 划分 |

## 6. 风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| 重放幂等性有隐藏漏洞（数据已改/WAL 未落的窗口） | 高 | D2 write-ahead 顺序 + 注入点单测先行；W4 专门安排"注入点×档位"矩阵 |
| msync/FlushViewOfFile 开销威胁 P99 ≤ 10μs | 中 | always 档每批一次而非每行；per_second 后台节流；W6 bench 提前量级验证，超标则调组提交窗口 |
| WalRing 覆盖协议复杂度超预期 | 中 | 强刷退化路径保底（覆盖即停写等 flush）；环容量配置化先给大默认值 |
| GCC/MSVC 差异再踩坑（如 auto 推导时点） | 低 | 显式返回类型约定沿用；CI 双平台每 PR 常绿 |
| 新增代码量大导致覆盖率跌破 85% | 中 | 同周测试纪律；W1/W2 基座即带全量单测 |
