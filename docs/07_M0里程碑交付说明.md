# 07 M0 里程碑交付说明

> 文档定位：记录 **M0「地基」** 阶段做了什么、工程设施如何就位，以及**编译后运行的预期结果**与
> **测试的预期结果**。目标读者：接手本库的开发者与执行 M0 验收的评审人。
> 里程碑定义见 [05 交付清单与里程碑计划](05_交付清单与里程碑计划.md) §3。

## 1. M0 目标回顾

| 项 | 内容 |
|---|---|
| 周期 | 约 4 周 |
| 范围 | platform / infra 全部；SharedBTree；Slab 分配器；CI 就绪 |
| 出口标准 | ① infra 单测全覆盖；② 两进程锁互斥 + 死亡恢复演示通过 |

M0 的定位是"地基"：不包含任何表/事务/网络能力（那分别是 M1/M2/M3 的主题），
只要求**多进程共享内存 + 跨进程锁 + 崩溃恢复 + 有序索引**这套底层机制可用、可测、可持续构建。

## 2. 交付清单与完成情况

### 2.1 运行时代码

| 组件 | 文件 | 提供的能力 |
|---|---|---|
| 公共头体系 | `include/rtdb/{version,result,err,options,api_macro}.hpp` | 分段错误码、`Result<T>` 跨界面无异常返回、打开参数、DLL 导出宏 |
| 平台抽象 | `src/platform/platform.hpp` | `SharedMemoryFile`（OpenOrCreate/CreateNew/OpenExisting、只读映射、区间 flush） |
| 进程身份 | `src/platform/platform_process.hpp` | PID + 进程启动时间双匹配（防 PID 复用）、活性探测、自身可执行文件路径 |
| Win32 实现 | `src/platform/win32/` | CreateFileW + CreateFileMappingW + MapViewOfFile；GetProcessTimes 取启动时间 |
| POSIX 实现 | `src/platform/posix/` | open + ftruncate + mmap(MAP_SHARED)；/proc/<pid>/stat 解析启动时间（无 /proc 退化为 kill(pid,0)） |
| 布局与自校验 | `src/infra/layout.hpp`、`shm_region.*` | 4096B 超级块、稳定字段 CRC32 自校验（magic→版本→字宽→CRC 逐级拒绝）、`session_count` 跨进程原子累计、"全零头部才初始化"（绝不静默覆盖外来/损坏映像） |
| Slab 分配器 | `src/infra/slab_allocator.*` | 12 级（32B~64KB）空闲链复用 + bump 线性切分、16B 自描述块头（释放免传尺寸）、magic 中毒检出双重释放、字节精确计账 |
| 根互斥锁 | `src/infra/shm_mutex.*` | CAS 快路径 + 指数退避；**死亡恢复**：持锁者崩溃后由存活进程判死（PID+启动时间双匹配）并 CAS 抢占，多恢复者竞争只决出唯一赢家 |
| 共享内存 B+ 树 | `src/infra/shared_btree.hpp` | 定长二进制键（int64 有序编码 / 字符串补零 memcmp 序）、点查、唯一约束、惰性删除、双端开闭范围游标（叶链）、主动分裂 + 根升级、`Validate()` 结构不变量校验、4096B 节点全 offset 寻址（跨进程零指针） |
| 引擎门面 | `include/rtdb/engine.hpp`、`src/engine.cpp` | Open（创建/校验/角色语义）、`committed_seq` / `session_count` 状态字、根锁与分配器直通句柄；PImpl 隐藏实现 |
| CRC32 | `src/infra/crc32.hpp` | IEEE 802.3 查表实现，仅用于布局自校验（非安全用途） |

## 3. M0 收尾阶段的变更记录

早期排错（提交记录"[Dev] M0开发中，进度未知"）遗留的临时手段在本阶段清理完毕：

1. **`AllocNode` 恢复整页清零**：新 B+ 树节点由"仅清前 64 字节（TEMP-DIAG）"恢复为
   4096 字节全页清零，未使用槽位/保留字段确定性归零，保证映像内容与分配历史无关；
2. **移除 `RTDB_BTREE_DEBUG` 环境变量调试开关**及其在插入/分裂/分配路径上的 4 处
   printf 追踪日志（防御路径 `DESCENT GUARD TRIP` 保留，仅在真 bug 时触发）；
3. **测试清洗**：移除逐键进度刷屏（`[prog]`）、重附着用例的无条件诊断打印
   （`[diag]`），并把"重开前结构校验"从打印升级为断言；仅失败路径的诊断输出保留
   （模型差分 `[model]`、缺键追踪 `[diag] missing=...`，只在用例即将失败时产生输出）；
4. **`InsertFindUniqueConstraint` 去除逐键双重插入诊断残留**（唯一约束行为本就有
   末尾 `kAlreadyExists` 断言覆盖，无覆盖损失）；
5. **头文件卫生**：`shm_mutex.hpp` 不再 `using namespace layout`（头文件命名空间
   污染），真正使用分区常量的翻译单元各自显式引入 `infra/layout.hpp`；
6. 全仓格式统一（见 §2.3）。

```
rtdb 0.1.0-m0 | instance=demo_instance.rtdb | sessions=1 committed_seq=0
(rerun to see session_count increase; tables arrive in M1)
```

## 5. 测试预期结果

### 5.1 总体预期

`ctest -C Release --output-on-failure`（**必须从 `build/` 目录执行**）应报告
**25 个用例全部通过**（`100% tests passed, 0 tests failed out of 25`）。
可用 `ctest -N` 先行核对用例清单；单套件可用
`ctest -R SharedBTreeInt --output-on-failure` 过滤。

预期耗时量级（i7 级单机）：全套约 **10~40 秒**；其中 `StressSplitsAndValidation`
（3 万键插入 + 周期性结构校验）与 `ThreadedContentionSerializes`
（4 线程 × 2.5 万次锁争用）占大头，均为秒级，不应出现分钟级停顿。

### 5.2 关键用例"成功长什么样"

| 用例 | 通过时意味着 |
|---|---|
| `EngineLifecycleTest.CreatePersistReopen` | 两次 Open 后 `SessionCount()==2`：数据与元数据真实落盘 |
| `EngineLifecycleTest.CorruptMagicRejected` | 人为破坏头部后 Open 返回 `kBadSuperBlock`：坏映像不会被静默重建覆盖 |
| `SlabTest.DoubleFreeDetectedViaHeaderPoisoning` | 双重释放被头部毒化机制当场拦截为 `kInternal` |
| `SharedBTreeInt.StressSplitsAndValidation` | 3 万随机键反复触发分裂/根升级后，层级/有序性/叶链/容量不变量全部成立 |
| `SharedBTreeInt.ReattachSeesSameContent` | 分配器重附着后 400 键全数可寻：进程重启后共享内存内容原样可用 |
| `MutexEnv.ThreadedContentionSerializes` | 10 万次加解锁全程并发重叠深度最大值恰为 1：锁语义没有被自旋/退避破坏 |

### 5.3 M0 出口演示：两进程锁互斥 + 死亡恢复（`RecoversAfterHolderHardKill`）

预期执行流：

1. 父进程先创建 1MB 映像；
2. `spawn_self` 以 `--rtdb-child-crash-lock <映像>` 派生**自身可执行文件**为子进程；
3. 子进程打开同一映像 → `LockRoot(5000)` 成功 → `quick_exit(9)` 硬退出
   （不经过任何析构/解锁路径，等价 `kill -9` 的"携锁死亡"，锁状态字残留）；
4. 父进程断言子进程退出码 == 9；
5. 父进程重新 Open 映像 → `RawRootMutex()->Lock(4000)` 必须在 4 秒内成功：
   死亡恢复路径生效（持有者 PID+启动时间双匹配确认已死 → CAS 抢占身份）；
6. 恢复者正常加解锁闭环，用例结束。

反向语义由同进程用例保证：持有者**活着**时，`Lock(1)` 得到 `kTimeout`、
`TryLock()` 返回 false——恢复分支绝不会误伤存活持有者。

### 5.4 失败时的定位手段

- 任何用例失败：`ctest --output-on-failure` 直接给出 gtest 断言上下文；
  B 树相关失败会附带 `[model]` / `[diag] missing=... trace=...` 失败路径诊断
  （正常通过时零输出）；
- CI 上失败：GitHub Actions 自动上传 `LastTest.log` artifact；
- B 树深度排查可临时启用 `DebugFindTrace`（测试内已接入失败路径）。

## 7. 已知边界与 M1 衔接

| 边界 | 说明 | 归属 |
|---|---|---|
| B 树只删不合并 | 惰性删除，空闲页复用与重平衡未实现（删除语义与计数已是准确的） | M1 重平衡/GC |
| `committed_seq` 静止 | 无事务提交点，恒为初始化值 | M1 WAL 接管 |
| Writer 角色只能挂既有映像 | 集群写者不隐式建映像，属当前有意语义 | M1 复核 |
| Reader 不挂分配器/锁 | 只读映射不触碰写侧元数据，`LockRoot` 返回 `kUnsupported` | 既定语义 |
| POSIX 路径未在 Linux 实机验证 | 代码就绪；/proc 启动时间解析的健壮性依赖 CI 首跑 | CI 首跑 |
| `Result<T>` 基于 `std::optional` | 仅宿主侧使用，共享内存结构不得包含 | 长期约定 |
| gtest 仅测试构建拉取 | `RTDB_BUILD_TESTS=OFF` 可完全离线构建核心库 | 既定策略 |
